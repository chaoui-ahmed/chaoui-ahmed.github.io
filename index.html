KV-Cache Compression for LLM Inference

Which cache-compression method should an LLM-native data system use — and does the answer depend on the workload?

The problem

Systems like Palimpzest and Lotus treat an LLM as a semantic operator: the same document gets filtered, then classified, then have fields extracted from it. Each operator re-sends the full document through the model, recomputing an identical context every time. Long documents and images make that expensive.

A compressed KV cache can be built once per document and reused across every later query — but only if compression preserves what those queries need.

What I built

A benchmark harness comparing three methods on the same footing via NVIDIA's kvpress: Expected Attention and KVzip (query-agnostic, so the cache is reusable) against Finch (query-dependent, so it specialises per request but cannot be reused).

Three datasets — 1,000 Rotten Tomatoes reviews, 1,000 Enron emails, and 63 paintings for the vision-language case — each with 10 filter and 10 extraction queries, across four models and compression ratios up to 80% of the cache evicted.

Result — no universal winner

Dataset / modelBest methodTypeMacro F1
Movie / Llama-3.2-1BKVzipquery-agnostic0.279
Email / Qwen2.5-0.5BExpected Attentionquery-agnostic0.273
Artwork / LLaVA-Next-8BFinchquery-dependent0.571
Artwork / Qwen3-VL-2BFinchquery-dependent0.484

The ranking flips with the modality. Query-agnostic methods take every text cell; the query-dependent method takes both vision-language cells by a wide margin. Image patch tokens appear to carry far more query-specific redundancy, which a method that sees the query can exploit and a reusable one cannot.

Two further findings: filter-style predicates survive 80% cache eviction with no measurable loss while extraction degrades steadily — so a real system should pick the ratio per operator, not globally. And Expected Attention runs 1.37× faster than KVzip (2.94 s vs 4.03 s mean, n=80 paired runs), because it scores in a single prefill pass where KVzip needs extra context-reconstruction passes.

A caveat I'd flag in review: filter and extraction metrics are disjoint here — F1 exists only for filter queries, accuracy only for extraction — so there is no single "system accuracy" number, and I don't quote one. Precision is also exactly 1.0 across all filter rows, meaning that F1 tracks recall alone.

Predictive Uncertainty via Deep Ensembles

Can an ensemble of plain networks — no Bayesian machinery — tell you when it doesn't know?

The problem

A model deployed anywhere consequential needs to signal its own uncertainty. The Bayesian route is principled but expensive. Lakshminarayanan et al. (2017) argued that simply ensembling independently-initialised networks gets you most of the way. I reimplemented it from scratch in JAX to see which parts hold.

What I tested

Three claims: that ensembles give calibrated predictive distributions on regression, that they flag out-of-distribution inputs, and that they stay trustworthy under adversarial perturbation. UCI regression across 20 random splits, then MNIST → notMNIST OOD detection with 10-network ensembles, with and without adversarial training.

Result — two of three reproduce

ClaimOutcome
Calibrated regression uncertaintyreproduces
OOD detection improves with ensemble sizereproduces
Confidence stays meaningful under attackdoes not hold

Under FGSM attack at ε = 0.3, accuracy restricted to high-confidence predictions is essentially flat — 7.4% at any threshold for the plain ensemble — and for the adversarially-trained one it declines past τ = 0.5, from 36.6% down to 26.2%. Filtering on confidence buys you nothing on adversarial inputs; the most confident predictions are among the least reliable.

What does hold is robustness: adversarial training lifts accuracy under attack from 7.4% to 35.3% at no cost on clean data (98.64% → 98.76% MNIST test accuracy).

Why this one taught me the most: the original figure in this project was generated by a hardcoded curve rather than measured accuracy. Finding that, re-running the experiment properly, and discovering the conclusion inverted is the reason every figure in my repositories is now written from a persisted results/*.json and asserted in CI.

Multimodal Match Prediction & Market Benchmarking

How close can a model built from public data get to a bookmaker's closing line — and is close enough to profit?

What I built

A late-fusion architecture: an LSTM over rolling match statistics (form, goals, shots on target, Elo, rest days) fused with 768-dimensional XLM-RoBERTa embeddings of pre-match news. Splits are strictly chronological and every feature is computed only from matches already played — look-ahead bugs are silent and flatter results, so the repository asserts their absence in tests.

Scaled to 37,514 matches across 14 European leagues, with the de-vigged opening price supplied as an input feature. That last choice makes the evaluation decisive: a model handed the market's own probabilities can only improve on them using information the market lacks.

Result — parity with the market, not an edge

PredictorLog-lossNote
Uniform prior1.0986floor
This model1.00165,429 held-out matches
Bookmaker closing line, de-vigged1.0006still ahead

The gap to the closing line narrowed from 0.0296 to 0.0010 — parity — but never turned negative. Given the price plus 22 features and 26,674 training matches, the model converges to reproducing the market. The conclusion is that this feature set carries no information the price has not already absorbed.

I validated that with a closing-line-value test against Pinnacle's close, the standard edge check. Model-selected bets returned −3.52% CLV versus −3.46% for a random-selection control: statistically indistinguishable from picking at random. The control is the load-bearing part — without it the raw number looks like signal.

Why value betting loses, mechanically: edge is p·odds − 1, so a fixed absolute error in p scales with the odds. A three-point overestimate implies a +20% edge at odds 15 but +2% at odds 1.5. Selecting on maximum edge therefore selects wherever your estimates are most inflated — claimed +28.6% EV at odds 10+ returned −32.1% actual — and Kelly sizes exactly those bets largest.

Sovereign Local AI for a City Administration

AI Engineering intern, DGSITN — Ville d'Épinal · summer 2025

The constraint that shaped everything

A French city administration cannot send municipal data to a foreign cloud LLM. Digital sovereignty was not a preference here but the requirement the whole architecture had to satisfy — which ruled out every hosted API and forced an entirely local, open-source stack.

Phase 1 — RAG over municipal documents

Give the assistant the ability to answer from the city's own publications. The first prototype used LangChain, and hit a version conflict with ChromaDB that made integration with the OpenWebUI front-end impossible.

Rather than work around it, I wrote the retrieval tool from scratch: PyPDF2 to extract text from municipal magazines, RecursiveCharacterTextSplitter for semantic chunking that preserves context across boundaries, all-MiniLM-L6-v2 for embeddings, and a persistent ChromaDB index. Slower to build, but it removed the dependency conflict and gave full control over indexing and retrieval.

Phase 2 — Connecting the IT service desk

The harder half. GLPI holds the city's ticketing data, but its REST API is limited and the underlying schema is large and poorly documented. I connected directly to the SQL database through Adminer and reverse-engineered it, producing an entity-relationship diagram over the tables that mattered — glpi_tickets, glpi_users, glpi_itilcategories — and used that as the reference for building reliable queries.

The client tool was built defensively: every API interaction opens a temporary session whose token is destroyed immediately afterwards, pagination is driven by reading the HTTP Content-Range header rather than guessing page counts, and ticket descriptions are stripped of HTML before reaching the model.

Phase 3 — Making it maintain itself

A knowledge base that goes stale is worse than none. I built an event-driven pipeline on Google Cloud: Cloud Scheduler triggers a Dockerised scraper on Cloud Run, new magazine PDFs land in a Cloud Storage bucket, and that write event triggers a second Cloud Run instance which re-indexes the document into ChromaDB.

The result closes the loop — an assistant grounded in both structured data (GLPI) and unstructured documents, whose knowledge base updates itself with no manual step.

Model adaptation and the public-facing assistant

Beyond retrieval, the open-weight model was fine-tuned on municipal data so it answered in the register and vocabulary the city actually uses, rather than relying on prompting alone. The citizen-facing assistant on epinal.fr was built on Dialogflow CX, with the local stack behind it handling grounded answers.
